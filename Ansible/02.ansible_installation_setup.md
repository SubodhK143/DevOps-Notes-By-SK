# Installation

## Ubuntu / Debian

```bash
sudo apt update
sudo apt install ansible -y
```
## Verify Installation

```bash
ansible --version
```
Example:

```text
ansible [core 2.x.x]
```

## Basic Ansible Configuration

Ansible can use a configuration file named:

```text
ansible.cfg
```
Common configuration locations:

```bash
./ansible.cfg
~/.ansible.cfg
/etc/ansible/ansible.cfg
```
Example:

```ini
[defaults]
inventory = ./inventory
host_key_checking = False
```
Check the active configuration:

```bash
ansible-config dump
```

## Ad-Hoc Commands

Ad-hoc commands are useful for quick one-time operations.

Check connectivity

```bash
ansible all -m ping
```
Run a command

```bash
ansible all -m command -a "uptime"
```
Check disk usage

```bash
ansible all -m shell -a "df -h"
```
Install a package

```bash
ansible web -m apt -a "name=nginx state=present" --become
```
Start a service

```bash
ansible web -m service -a "name=nginx state=started" --become
```

| Module | Purpose |
|---|---|
| `ping` | Test Ansible connectivity |

| `template` | Generate files using Jinja2 |

| `group` | Manage groups |

## Playbooks

A playbook is a YAML file containing one or more plays.

Example:

```yml
---
- name: Install Nginx
  hosts: web
  become: true

  tasks:
    - name: Install Nginx
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: Start Nginx
      ansible.builtin.service:
        name: nginx
        state: started
```
Run a playbook:

```bash
ansible-playbook -i inventory site.yml
```
---

## Playbook Structure

```text
Playbook
   |
   +── Play
   |    |
   |    +── hosts
   |    +── become
   |    +── vars
   |    +── tasks
   |           |
   |           +── Task
   |           +── Task
   |
   +── Play
```
Basic structure:

```yaml
- name: Configure web servers
  hosts: web
  become: true

  tasks:
    - name: Install package
      ansible.builtin.apt:
        name: nginx
        state: present
```

## Task

A task is a single unit of work.

Example:

```yaml
- name: Install Nginx
  ansible.builtin.apt:
    name: nginx
    state: present
```
A playbook can contain many tasks:

```yaml
tasks:
  - name: Install Nginx
    ansible.builtin.apt:
      name: nginx
      state: present

  - name: Start Nginx
    ansible.builtin.service:
      name: nginx
      state: started
```
---

## Idempotency

Idempotency means running the same automation multiple times should not repeatedly change the system once the desired state has been reached.

Example:

```yaml
- name: Ensure Nginx is installed
  ansible.builtin.apt:
    name: nginx
    state: present
```
First run: `changed=1`
Second run: `changed=0`

The goal is:

```text
Desired State
     ↑
     |
Automation
     |
     +---- Run 1 → Change
     |
     +---- Run 2 → No unnecessary change
     |
     +---- Run 3 → No unnecessary change
```

## Privilege Escalation

Ansible can execute tasks with elevated privileges using become.

Example:

```yml
- name: Install Nginx
  hosts: web
  become: true

  tasks:
    - name: Install Nginx
      ansible.builtin.apt:
        name: nginx
        state: present
```
Ad-hoc command:

```bash
ansible web -m apt -a "name=nginx state=present" --become
```
Common options:

```bash
--become
--ask-become-pass
```

## Common Ansible Commands

| Task | Command |
|---|---|
| **Check version** | `ansible --version` |
| **List inventory** | `ansible-inventory --list` |
| **Test hosts** | `ansible all -m ping` |
| **Run ad-hoc command** | `ansible all -m command -a "uptime"` |
| **Run playbook** | `ansible-playbook playbook.yml` |

## # Ansible vs Shell Scripts

| Ansible | Shell Script |
|---|---|
| Declarative | Mostly imperative |
| YAML-based | Shell syntax |
| Built-in modules | Commands/tools |
| Idempotency support | Must implement manually |
| Multi-host execution | Usually requires custom logic |
| Reusable roles | Functions/scripts |
| Inventory management | Usually manual |

Use Ansible when you need **repeatable, scalable configuration and orchestration across multiple systems**.

## # Ansible vs Terraform

Ansible and Terraform solve different problems.

| Terraform | Ansible |
|---|---|
| Infrastructure provisioning | Configuration management |
| Creates infrastructure | Configures existing infrastructure |
| Declarative | Declarative |
| Uses providers | Uses modules/collections |
| Manages infrastructure state | Generally does not maintain infrastructure state |
| Example: Create EC2 | Example: Configure Nginx on EC2 |

They are often used together:

```text
Terraform
    ↓
Provision Infrastructure
    ↓
EC2 / VPC / Load Balancer
    ↓
Ansible
    ↓
Configure Servers
    ↓
Install & Configure Applications
```

## # Best Practices

- Use **YAML playbooks** instead of excessive ad-hoc commands.
- Use fully qualified module names such as `ansible.builtin.copy`.
- Keep inventories separate from playbooks.
- Use variables instead of hardcoding values.
- Use roles for reusable automation.
- Use Ansible Vault for secrets.
- Prefer idempotent modules over raw shell commands.
- Use `--check` before applying risky changes.
- Use `--diff` when reviewing configuration changes.
- Keep playbooks under version control.
- Use meaningful names for plays and tasks.
- Follow the principle of least privilege.
- Test automation before applying it to production.
