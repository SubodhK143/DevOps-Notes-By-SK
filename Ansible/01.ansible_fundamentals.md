# 01. Ansible Fundamentals

Ansible is an **open-source automation and configuration management tool** used to automate provisioning, configuration, application deployment, and repetitive IT tasks.

## Why Ansible?

- **Agentless** — no Ansible agent required on managed nodes
- **Simple** — uses human-readable YAML
- **Idempotent** — repeated runs aim for the same desired state
- **SSH-based** — Linux/Unix nodes commonly use SSH
- **Scalable** — manage one server or thousands
- **Extensible** — modules, plugins, roles, and collections

## Ansible Architecture

```text
                    ┌─────────────────────┐
                    │   Ansible Control   │
                    │        Node         │
                    │                     │
                    │  ansible.cfg        │
                    │  Inventory          │
                    │  Playbooks          │
                    │  Roles              │
                    └──────────┬──────────┘
                               │
                    SSH / WinRM / Other
                               │
             ┌─────────────────┼─────────────────┐
             │                 │                 │
             ▼                 ▼                 ▼
       ┌──────────┐      ┌──────────┐      ┌──────────┐
       │ Web      │      │ App      │      │ DB       │
       │ Server   │      │ Server   │      │ Server   │
       └──────────┘      └──────────┘      └──────────┘
         Managed           Managed           Managed
           Node              Node              Node
```

## Key Components

| Component | Purpose |
|-----------|---------|
| Control Node | Machine where Ansible runs |
| Managed Node | Server/device managed by Ansible |
| Inventory | Defines managed hosts and groups |
| Module | Performs a specific task |
| Task | Executes a module |
| Play | Maps tasks to hosts |
| Playbook | YAML file containing one or more plays |
| Role | Reusable Ansible structure |
| Collection | Package of Ansible content |
| `ansible.cfg` | Ansible configuration |

---

## Control Node vs Managed Node

| Control Node | Managed Node |
|--------------|--------------|
| Machine from which Ansible commands are run | Target machine managed by Ansible |
| Runs Ansible | Receives and executes tasks |
| Requires Ansible installed | Generally does not require Ansible installed |
| Examples: laptop, EC2, server | Examples: web-server, app-server, db-server |

### Control Node

The machine from which you run:

```bash
ansible
ansible-playbook
ansible-galaxy
ansible-vault
```
### Managed Node

The target machine on which Ansible performs tasks.

Examples:

```text
web-server
app-server
db-server
```
> **Note:** Managed Linux nodes generally do not need the Ansible package installed.

## Agentless Architecture

Traditional configuration-management tools may require an agent on every server.

Ansible uses an **agentless approach**:

```text
Control Node
     │
     │ SSH
     ▼
Managed Node
```

## How Ansible Works

A typical workflow:

```text
Inventory
   ↓
Playbook
   ↓
Task
   ↓
Module
   ↓
Managed Node
   ↓
Desired State
```
Example:

```yaml
- name: Install Nginx
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.dnf:
        name: nginx
        state: present
```
Ansible checks the current state and takes action only when required.

---

## Idempotency

Idempotency means running the same automation multiple times should not repeatedly change the system once the desired state has been reached.

Example:

```yaml
- name: Ensure nginx is installed
  ansible.builtin.dnf:
    name: nginx
    state: present
```

First run:

```text
nginx not installed
        ↓
     Install
        ↓
       OK
```

Next run:

```text
nginx already installed
        ↓
     No change
```

This is one of Ansible's most important concepts.

## Modules

Modules are the building blocks used by Ansible to perform tasks.

### Common Modules

| Module | Purpose |
|--------|---------|
| `ping` | Test connectivity |
| `command` | Run a command |
| `shell` | Run shell commands |
| `copy` | Copy files |
| `file` | Manage files/directories |
| `template` | Generate files using Jinja2 |
| `dnf` | Manage RPM packages |
| `service` | Manage services |
| `user` | Manage users |
| `debug` | Display information |
| `setup` | Gather system facts |

Example:

```yaml
- name: Install nginx
  ansible.builtin.dnf:
    name: nginx
    state: present
```
Using the **Fully Qualified Collection Name (FQCN)** such as:

```yaml
ansible.builtin.dnf
```
is recommended for clarity and maintainability.

## Inventory

Inventory defines the systems Ansible manages.

Example:

```INI

web02

[app]
app01

[db]
db01
```
Run:

```bash
ansible-inventory --graph
```
Test connectivity:

```bash
ansible all -m ansible.builtin.ping
```

## Playbooks

A **playbook** is a YAML file that describes the desired configuration.

### Example

```yaml
---
- name: Configure web servers
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.dnf:
        name: nginx
        state: present

    - name: Start nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

Run a Playbook
 
```bash
ansible-playbook playbook.yml
```

## Ansible Configuration

Ansible uses `ansible.cfg` for configuration.

### Common Settings

```ini
[defaults]
inventory = inventory.ini
remote_user = ec2-user
host_key_checking = False
interpreter_python = auto_silent
```
- **`inventory`** → Defines the inventory file.
- **`remote_user`** → User Ansible uses to connect to managed nodes.
- **`host_key_checking`** → Controls SSH host-key verification.
-  **`interpreter_python`** → Controls Python interpreter discovery on managed nodes.

## Ansible vs Shell Scripts

| Shell Scripts | Ansible |
|---------------|---------|
| Imperative | Desired-state oriented |
| Harder to maintain at scale | Designed for infrastructure automation |
| Manual error handling | Modules provide structured behavior |
| Limited inventory management | Built-in inventory |
| Reusability requires scripting | Roles and collections |
| Idempotency must be implemented manually | Modules commonly support idempotent behavior |

- **Ansible** is primarily **agentless**.
- **Linux managed nodes** commonly use **SSH**.

- **Modules** perform operations.
- **Tasks** call modules.
- **Plays** target hosts and define tasks.
- **Playbooks** contain one or more plays.
- **Roles** provide reusable structure.
- **Idempotency** prevents unnecessary changes.
- `ansible` is commonly used for **ad-hoc commands**.
- `ansible-playbook` executes **playbooks**.
