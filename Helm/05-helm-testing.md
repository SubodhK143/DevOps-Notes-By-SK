# Helm Testing — Validate Charts Before Deployment

Helm testing helps verify that a Helm chart is:

- Structurally valid
- Rendering correctly
- Producing valid Kubernetes manifests
- Deploying successfully
- Functionally behaving as expected

A practical Helm validation flow is:

```text
Chart
  ↓
helm lint
  ↓
helm template
  ↓
helm install --dry-run
  ↓
helm install
  ↓
helm test
  ↓
Verify Application
```

---

# Why Test Helm Charts?

A Helm chart can contain:

```text
Templates
Values
Conditions
Loops
Dependencies
Hooks
Kubernetes Resources
```

A small template mistake can cause a deployment failure.

Testing helps catch problems before production.

Examples:

- Invalid YAML
- Missing values
- Incorrect template logic
- Wrong resource configuration
- Invalid Kubernetes API versions
- Broken service connectivity
- Incorrect application behavior

---

# Helm Testing Levels

Helm testing can be divided into several levels:

```text
Level 1 → Chart Linting
Level 2 → Template Rendering
Level 3 → Dry Run
Level 4 → Kubernetes Validation
Level 5 → Helm Test
Level 6 → Application Verification
```

---

# 1. Helm Lint

`helm lint` checks a chart for possible issues.

```bash
helm lint ./my-app
```

Example:

```text
==> Linting ./my-app
[INFO] Chart.yaml: icon is recommended
1 chart(s) linted, 0 chart(s) failed
```

A successful lint does **not** guarantee that the application will work.

It only means the chart passed the checks performed by Helm.

---

# 2. Lint with Values

Test using a custom values file:

```bash
helm lint ./my-app \
  -f values-dev.yaml
```

Multiple values files:

```bash
helm lint ./my-app \
  -f values.yaml \
  -f values-prod.yaml
```

Test CLI overrides:

```bash
helm lint ./my-app \
  --set replicaCount=5
```

---

# 3. Template Rendering

`helm template` renders the chart locally without installing it.

```bash
helm template my-release ./my-app
```

This shows the Kubernetes manifests Helm would generate.

Example:

```text
values.yaml
     ↓
Helm Templates
     ↓
helm template
     ↓
Rendered Kubernetes YAML
```

This is one of the most useful Helm debugging commands.

---

# Save Rendered Output

Save the generated YAML:

```bash
helm template my-release ./my-app > rendered.yaml
```

Inspect:

```bash
cat rendered.yaml
```

This allows you to review the exact Kubernetes manifests generated by Helm.

---

# Render with Custom Values

```bash
helm template my-release ./my-app \
  -f values-prod.yaml
```

Override a value:

```bash
helm template my-release ./my-app \
  --set replicaCount=5
```

---

# Debug Template Rendering

Use:

```bash
helm template my-release ./my-app \
  --debug
```

This provides additional information when troubleshooting template errors.

---

# 4. Dry-Run Installation

A dry run simulates an installation without actually deploying the release.

```bash
helm install my-release ./my-app \
  --dry-run
```

For more debugging information:

```bash
helm install my-release ./my-app \
  --dry-run \
  --debug
```

Useful for detecting:

- Template errors
- Missing values
- Incorrect rendering
- Installation-time problems

---

# Dry Run vs Template

| Command | Purpose |
|---|---|
| `helm template` | Render templates locally |
| `helm install --dry-run` | Simulate an installation |

Think:

```text
helm template
     ↓
"What YAML will Helm generate?"

helm install --dry-run
     ↓
"What would this installation look like?"
```

---

# 5. Kubernetes Validation

Helm can render correct YAML that still contains Kubernetes configuration problems.

After rendering, validate the generated manifests using Kubernetes tooling.

Example:

```bash
helm template my-release ./my-app > rendered.yaml
```

Then inspect:

```bash
kubectl apply --dry-run=client -f rendered.yaml
```

This validates the manifests from the client perspective without creating resources.

For cluster-aware validation:

```bash
kubectl apply --dry-run=server -f rendered.yaml
```

Server-side validation is useful because the Kubernetes API server can validate the manifests against the actual cluster.

---

# 6. Helm Tests

Helm supports application-level tests using **test hooks**.

A Helm test is usually a Kubernetes `Job` annotated with:

```yaml
"helm.sh/hook": test
```

Example:

```yaml
apiVersion: batch/v1
kind: Job

metadata:
  name: {{ .Release.Name }}-test

  annotations:
    "helm.sh/hook": test

spec:
  template:
    spec:
      restartPolicy: Never

      containers:
        - name: test
          image: busybox:1.36
          command:
            - sh
            - -c
            - echo "Helm test passed"
```

---

# Running Helm Tests

First install the chart:

```bash
helm install my-app ./my-app
```

Then run:

```bash
helm test my-app
```

Example:

```text
NAME: my-app
LAST DEPLOYED: ...
NAMESPACE: default
STATUS: deployed
```

The test Job executes and reports whether the test succeeded or failed.

---

# Helm Test Flow

```text
helm install
      ↓
Application deployed
      ↓
helm test
      ↓
Test Job created
      ↓
Application checked
      ↓
PASS / FAIL
```

# Test Job Example

Suppose an application exposes HTTP on port `80`.

A test can use a container to make a request.

```yaml
apiVersion: batch/v1
kind: Job

metadata:
  name: {{ .Release.Name }}-connection-test

  annotations:
    "helm.sh/hook": test
    "helm.sh/hook-delete-policy": hook-succeeded

spec:
  template:
    spec:
      restartPolicy: Never

      containers:
        - name: connection-test
          image: busybox:1.36

          command:
            - sh
            - -c
            - |
              wget -qO- http://{{ .Release.Name }}:80
```

If the request succeeds, the test Job exits successfully.

---

# Test Using a Service

Example:

```yaml
command:
  - sh
  - -c
  - |
    wget -qO- http://{{ .Release.Name }}:80
```

This verifies that the application Service is reachable from inside the cluster.

---

# Test Cleanup

Test Jobs can remain after execution.

Use:

```yaml
"helm.sh/hook-delete-policy": hook-succeeded
```

Example:

```yaml
annotations:
  "helm.sh/hook": test
  "helm.sh/hook-delete-policy": hook-succeeded
```

To keep failed test Jobs for debugging:

```yaml
annotations:
  "helm.sh/hook": test
  "helm.sh/hook-delete-policy": hook-succeeded
```

If the Job fails, it is not removed by `hook-succeeded`, allowing you to inspect it.

# Testing Dependencies

If the chart has dependencies:

```bash
helm dependency build ./my-app
```

Then:

```bash
helm lint ./my-app
```

Render:

```bash
helm template my-app ./my-app
```

This helps ensure dependencies are available and render correctly.

---

# Testing Conditional Resources

Suppose `values.yaml` contains:

```yaml
ingress:
  enabled: false
```

Template:

```gotemplate
{{ if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
...
{{ end }}
```

Test disabled:

```bash
helm template my-app ./my-app \
  --set ingress.enabled=false
```

Test enabled:

```bash
helm template my-app ./my-app \
  --set ingress.enabled=true
```

This is important because different values can produce completely different Kubernetes resources.

---

# Testing Required Values

If the template uses:

```gotemplate
{{ required "image.repository is required" .Values.image.repository }}
```

Test without the value:

```bash
helm template my-app ./my-app \
  --set image.repository=""
```

Helm should report an error.

This confirms that the required-value validation works.

# Testing Upgrades

Testing should not stop at installation.

Test:

```text
Install
   ↓
Upgrade
   ↓
Test
   ↓
Rollback
   ↓
Test Again
```

Example:

```bash
helm install my-app ./my-app
```

Upgrade:

```bash
helm upgrade my-app ./my-app \
  --set replicaCount=5
```

Check:

```bash
helm status my-app
```

Run tests:

```bash
helm test my-app
```

---

# Testing Rollbacks

Check release history:

```bash
helm history my-app
```

Rollback:

```bash
helm rollback my-app 1
```

Check:

```bash
helm status my-app
```

Run:

```bash
helm test my-app
```

This verifies that the rolled-back version still works.

# Helm Testing in CI/CD

Helm testing fits naturally into CI/CD.

Example:

```text
Git Push
   ↓
CI Pipeline
   ↓
Checkout
   ↓
Install Dependencies
   ↓
helm lint
   ↓
helm template
   ↓
Kubernetes Validation
   ↓
Deploy to Test Cluster
   ↓
helm test
   ↓
PASS
   ↓
Production Deployment
```

Example commands:

```bash
helm dependency build ./my-app

helm lint ./my-app

helm template my-app ./my-app > rendered.yaml

kubectl apply --dry-run=server -f rendered.yaml

helm upgrade --install my-app ./my-app

helm test my-app
```

---

# Example CI Testing Script

```bash
#!/bin/bash

set -e

CHART="./my-app"
RELEASE="my-app"

echo "Linting chart..."
helm lint "$CHART"

echo "Rendering templates..."
helm template "$RELEASE" "$CHART" > rendered.yaml

echo "Validating Kubernetes manifests..."
kubectl apply --dry-run=server -f rendered.yaml

echo "Installing chart..."
helm upgrade --install "$RELEASE" "$CHART"

echo "Running Helm tests..."
helm test "$RELEASE"

echo "Helm tests passed!"
```

`set -e` causes the script to stop when a command returns a non-zero exit status.

# Testing Pyramid for Helm

A practical testing strategy:

```text
              Application Tests
                    ▲
                    │
                Helm Tests
                    ▲
                    │
           Kubernetes Validation
                    ▲
                    │
             Template Rendering
                    ▲
                    │
                Helm Lint
```

Start with fast checks and progressively move toward real deployment validation.

---

# What Each Test Catches

| Test | Helps Detect |
|---|---|
| `helm lint` | Chart structure and common chart issues |
| `helm template` | Template rendering problems |
| `helm install --dry-run` | Installation/rendering issues |
| `kubectl apply --dry-run` | Kubernetes manifest validation issues |
| `helm test` | Application/service behavior |
| Real deployment | Cluster/runtime issues |

No single test catches everything.

---

# Helm Testing vs Helm Lint

These are different.

### `helm lint`

Checks the chart itself:

```bash
helm lint ./my-app
```

### `helm test`

Checks the deployed application using a test resource:

```bash
helm test my-app
```

Think:

```text
lint → Is the chart structured correctly?

test → Does the deployed application behave correctly?
```

# Best Practices

### 1. Always lint

```bash
helm lint ./my-app
```

---

### 2. Always inspect rendered YAML

```bash
helm template my-app ./my-app
```

---

### 3. Validate against Kubernetes

```bash
kubectl apply --dry-run=server -f rendered.yaml
```

---

### 4. Add meaningful Helm tests

Do not create tests that only print:

```text
Test passed
```

Prefer tests that verify actual behavior:

```text
Service connectivity
HTTP response
Database connectivity
Application health
Required endpoint
```

---

### 5. Test upgrades

Do not test only:

```bash
helm install
```

Also test:

```bash
helm upgrade
helm rollback
```

---

### 6. Keep tests independent

A test should verify one clear behavior whenever practical.

---

### 7. Clean up successful test resources

Use:

```yaml
"helm.sh/hook-delete-policy": hook-succeeded
```

---

### 8. Keep failed resources when debugging

Avoid automatically deleting failed test Jobs until you have finished troubleshooting.

---

### 9. Run tests in CI/CD

Helm validation should happen before production deployment.

# Common Mistakes

## Mistake 1 — Only Running `helm lint`

A chart can pass linting and still fail when deployed.

Use:

```bash
helm lint
helm template
helm test
```

---

## Mistake 2 — Not Testing Values

A chart may work with default values but fail with production values.

Test:

```bash
helm template my-app ./my-app \
  -f values-prod.yaml
```

---

## Mistake 3 — Testing Only Installation

Upgrades can introduce different problems.

Test:

```text
Install
Upgrade
Rollback
```

---

## Mistake 4 — Test Does Not Check Anything

This:

```bash
echo "Application works"
```

does not actually verify the application.

A useful test should perform a real check.

# Key Takeaways

- `helm lint` checks the chart for common issues.
- `helm template` renders templates without deploying.
- `helm install --dry-run --debug` simulates an installation.
- `kubectl apply --dry-run=server` can validate rendered manifests against the Kubernetes API server.
- `helm test` runs application-level tests using Helm test hooks.
- Helm tests are commonly implemented as Kubernetes Jobs.
- Test Jobs can verify real application behavior such as HTTP connectivity.
- Test failures should be investigated using `kubectl describe` and `kubectl logs`.
- Test different `values.yaml` configurations, especially production values.
- Test **install, upgrade, and rollback**, not just installation.
- Helm testing is especially valuable in CI/CD pipelines.

> **Remember:**
>
> **Lint → Validate the Chart**  
> **Template → Validate the Rendering**  
> **Dry Run → Simulate Deployment**  
> **Kubectl Validation → Validate Kubernetes Manifests**  
> **Helm Test → Verify Application Behavior**  
> **CI/CD → Automate the Entire Process**
